# Tasks: Delivery by e-mail and Telegram, the cooperative's bot (017)

Rules for every slice: contract first (`api/openapi.yaml`, tag `notifications`, then `make gen`); schema only through new
Flyway migrations — `V29__delivery.sql` (written in Slice 1 with every 017 table, the discovery function and the
permission) and `V30__jobrunr.sql` (Slice 3); a later slice adds V31+ only if needed, never edits an applied one; every
new cooperative table has `tenant_id`, RLS, `tenant_isolation`, a tenant index and an isolation test; every screen text
through the i18n catalogs (uk default, both catalogs); member messages and e-mails only from the Ukrainian backend
bundle `resources/notifications/messages_uk.properties`; secrets (SMTP password, bot token) sealed through
`PersonalDataCipher`, never in API responses, logs or audit values; chat ids sealed with a blind index; delivery rows
hold ids and codes only; no message texts or personal data in logs; permissions, never role names; tests never reach
the real Telegram or a real mailbox (in-JVM fake Bot API and Mailpit in Testcontainers); new dependencies only
`spring-boot-starter-mail` (Boot-managed) and `org.jobrunr:jobrunr-spring-boot-4-starter:9.0.1`, pinned exactly;
docker images pinned to exact tags verified with `docker pull`; no edits to generated code, `.github/`, `CLAUDE.md` or
`.claude/`; Conventional Commits, no AI attribution in commits. Builders run only the slice's Verify command and the
tests of the classes they changed — never the full backend suite (`./mvnw verify`, `make test`, `make check`); the full
suite runs once in Phase 4. Every Verify task stops anything it started and deletes its own temporary files.
References "TC x.y" are sections of `technical-considerations.md`; "FS x.y" of `functional-spec.md`.
