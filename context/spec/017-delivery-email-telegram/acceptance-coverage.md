- Gaps: none. Every criterion that can be tested is met by the implementation.

## Notes on behaviour found while writing the acceptance tests (not gaps)

- A second send of the month after a member's bot was blocked creates one new row for that member: the blocked bot
  ended the link, so the member now resolves through the fallback channel of FS 2.3 (e-mail when they have one, else
  paper). Nobody gets the same invoice twice through the same channel; the invoice that failed is not sent again by the
  month's send, only by «Надіслати ще раз».
- The announcement and the delivery rows are only read through the delivery worker; the e2e specs wait for the
  fake Telegram server and the mail catcher instead of sleeping.
- E2E specs use a chat id range of their own and never call the fake server's `/control/reset`: the application keeps
  the id of the last update it took, so a server that restarts its numbering would look like "nothing new" to the bot.
