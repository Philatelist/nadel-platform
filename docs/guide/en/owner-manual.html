1 How the platform is built

One platform serves many cooperatives. Each cooperative's data is kept apart by the database itself.

Web client
The board's screens and the member's account. It calculates nothing; it shows what the server returns.
Backend
One application (a modular monolith) with the modules tenancy (cooperatives), identity (sign-in and permissions), members, plots, settings, imports, tariffs, meters, money, audit. A test guards the module boundaries.
API contract
api/openapi.yaml is the single source of truth: the server interfaces and the web and app client are generated from it.
PostgreSQL
All data. Every table with cooperative data has a tenant_id and an RLS policy: a query only sees its own cooperative's rows.
Keycloak
Accounts, passwords, sign-in. Cooperative roles are not kept in Keycloak but in the database; Keycloak holds only the platform operator role.
Mobile app
An Expo shell exists; the real app is phase 5.

How a request flows

  1. A person signs in through Keycloak and gets a token with the tenant_id attribute (their cooperative).
  2. The backend checks the token, finds the member by email and takes their permissions from the database.
  3. For the request the database receives the tenant_id; RLS lets through only that cooperative's rows.
  4. Board changes are published as events; the audit module records them through an "outbox", so no event is lost even if the server restarts.

Docker Desktop, JDK 25, Node.js 22 and pnpm, Git, the GitHub CLI (gh). Repository: ~/IdeaProjects/nadel-platform.

The local master key (infra/.env)

Members' contacts are stored encrypted (chapter 8). The first time make up, make backend or make e2e runs, it creates the file infra/.env with one line, NADEL_PD_MASTER_KEY=…, a random local key. The file is git-ignored, has mode 600 and is read only by the backend process. An existing file is never overwritten.

  • Never commit this file and never paste the key into a chat or a ticket.
  • If you delete it, the contacts already in the local database become unreadable (the backend refuses to start with PD_MASTER_KEY_MISMATCH, chapter 12). Then reset the local database too (below) — it is only demo data.

Resetting the local database

make down && docker compose -f infra/docker-compose.yml down -v && make up

Erases all local data; migrations and demo data load again and Keycloak imports the realm again. Needed after changing infra/keycloak/nadel-realm.json or when test data has spoiled the demo.

PostGIS image on a Mac with Apple Silicon

The default image postgis/postgis:17-3.5 exists only for Intel (linux/amd64); on an M-series Mac Docker runs it emulated, and the database, the backend tests included, is several times slower. Both the local stack and the backend tests (Testcontainers) take the image from the environment variable NADEL_POSTGIS_IMAGE. On a Mac put the multi-architecture build of the same PostgreSQL 17 + PostGIS 3.5 into the shell profile (~/.zshrc): 

export NADEL_POSTGIS_IMAGE=imresamu/postgis:17-3.5

It is built by a maintainer of the official PostGIS images from the same sources. After switching, reset the local database once (above): a data volume is not moved between processor architectures. CI and servers keep the default image.

3 Keycloak: sign-in and accounts

Keycloak keeps accounts and passwords. The platform's realm is nadel with two clients, nadel-web and nadel-mobile. Sign-in is by email, self sign-up is off, password reset by email is allowed (it works once mail is configured), the sign-in page speaks Ukrainian (default) and English.

How an account is tied to a cooperative

  • The user attribute tenant_id is the cooperative's identifier. It goes into the token, and the backend works only with that cooperative's data.
  • The member is found by email: the email in Keycloak must match the email on the member card (any letter case). The backend remembers the link at the first sign-in. The first chairman of a new cooperative is linked differently, by the Keycloak user's identifier (chapter 4).
  • Roles and permissions live in the cooperative's database, not in Keycloak. The exception is the PLATFORM_OPERATOR role.

Creating an account for a member

  1. Make sure the member exists in the system and their card has an email (the chairman does this).
  2. Keycloak admin console → choose the realm nadel at the top left → Users → Add user.
  3. Username and Email — the same address; First name, Last name; switch on Email verified; Create.
  4. Tab Attributes: key tenant_id, value — the cooperative's identifier (chapter 4) → Save.
  5. Tab Credentials → Set password: a temporary password with Temporary on — the person sets their own at the first sign-in.
No Attributes tab?

Keycloak 26 hides custom attributes by default. Once: Realm settings → General → Unmanaged attributes → "Admin can edit" → Save.

Other tasks

Task Where
Reset a password Users → user → Credentials → Reset password (Temporary)
Block sign-in Users → user → switch off Enabled. Archiving the member in the system also blocks sign-in.
End all sessions Users → user → Sessions → Sign out
Make someone the platform operator Users → user → Role mapping → Assign role → PLATFORM_OPERATOR; no tenant_id attribute
Change realm settings for good Edit infra/keycloak/nadel-realm.json and reset the local database (chapter 2): the file is imported only into an empty Keycloak

Creating accounts and email invitations from the cooperative admin come with the operator console and mail (phases 4 and 7). Until then the platform owner creates accounts in Keycloak.

4 Cooperatives: creation and isolation

A cooperative (a tenant in the code) is a row in the tenant table with an identifier (UUID) and a name. When a cooperative is created the system gives it the base roles, the settings and the standard charge types.

Creating a new cooperative (until the operator console exists)

Contacts (phones, email, address) are encrypted by the application, so SQL cannot write them. The first chairman is therefore created without contacts and is linked to the Keycloak account by the account's identifier; the chairman enters the email and phones in the app afterwards.

  1. Connect to the database as the superuser: docker compose -f infra/docker-compose.yml exec postgres psql -U postgres -d nadel.
  2. Create the cooperative, with the name filled in, and note the identifier from the message:
DO $$
DECLARE t uuid := gen_random_uuid();
BEGIN
  INSERT INTO tenant (id, name) VALUES (t, 'СТ «Назва»');
  PERFORM seed_base_roles(t);          -- roles, settings, charge types
  RAISE NOTICE 'tenant_id = %', t;
END $$;
  1. Create the chairman's account in Keycloak with the attribute tenant_id set to that identifier (chapter 3). Open the new user and copy the ID shown on the Details tab (a UUID) — it is the Keycloak subject.
  2. Back in psql, add the chairman with the identifier and the subject (name and both values filled in): 
DO $$
DECLARE t uuid := '<tenant_id>'; m uuid := gen_random_uuid();
BEGIN
  INSERT INTO member (id, tenant_id, last_name, first_name, delivery_channel, keycloak_subject)
  VALUES (m, t, 'Last name', 'First name', 'PAPER', '<Keycloak user ID>');
  INSERT INTO member_role (tenant_id, member_id, role_id)
  SELECT t, m, id FROM role WHERE tenant_id = t AND base_code = 'CHAIRMAN';
END $$;
  1. The chairman signs in (the subject links the account to the card) and opens "Members" → their own card → "Edit" to enter the email, phones and the preferred channel; the app encrypts them. Then the Excel import, members, tariffs and meters.

The cooperative's encryption keys are created by the server the first time the cooperative needs them (for example when the chairman saves the first contact); there is nothing to do for them here. The delivery channel stays "Paper" until a contact exists, because the database rejects a channel without its contact.

A temporary way

This SQL is a workaround until the operator console; creation through it is not in the audit log. On the server a "first cooperative" command replaces it (chapter 9), later the operator console.

Isolation

  • The application talks to the database as nadel_app, which cannot bypass RLS; migrations run as nadel_owner.
  • Every new table has an isolation test: another cooperative's data is invisible even to a direct query.
  • Deleting a cooperative is not provided; the data stays until an archiving decision (phase 7).

5 The platform operator partly

The operator is the person who runs the platform (you). The principle (ADR 0008): the operator does not see cooperative data — no members, no plots, no money.

What State
Signing in as operator@nadel.local: the app says "No cooperative", data is unavailable works
Operator console: list of cooperatives, creating a cooperative and its chairman, blocking phase 7
Platform reports without personal data: number of cooperatives, plots, active users, storage used, subscription state phase 7
Support access: a chairman grants temporary access to their cooperative; every action goes to their audit log phase 7
Subscriptions and payment for using the platform phase 7

Until then the operator's technical tasks are Keycloak (chapter 3), creating cooperatives (chapter 4), the server and backups (chapter 9).

Documents: requisites, fonts, the PDF engine

  • Requisites. The IBAN, the name, the address and the bank are entered by the chairman in Settings. The EDRPOU code belongs to the cooperative's own record and only the platform operator sets it; until the operator console exists, the owner writes it into the edrpou column of the cooperative's tenant row as the database owner. Invoices are not built without both.
  • Language. Documents are always in Ukrainian, whatever the language of the user's screens: they are official documents. Only the screens follow the language the user chose.
  • Fonts. PDFs embed a subset of IBM Plex Sans (the font of the app's design), licensed under the SIL Open Font License 1.1. The font files and the licence text are in the backend resources and must travel together. Cyrillic and the hryvnia sign are readable without any font on the reader's computer.
  • The PDF engine is Apache PDFBox. A PDF is not stored: it is drawn on each download from the data kept at build time, and the same version always gives the same file (apart from the technical creation date). The QR image is made with ZXing; the layout follows the National Bank of Ukraine rules (format 003).
  • The build limit. A month's invoices are built in one request while the treasurer waits. The measured limit for the largest supported cooperative: see ADR 0017 (docs/adr/0017-documents.md).
  • Permissions. "Issue invoices" (chairman and treasurer by default) builds, re-issues and prints invoices; "Issue certificates" (chairman) issues and annuls certificates. Viewing needs "View charges", and printing a receipt "View payments". Custom roles can be given both on the roles screen.

  • The chairman always holds every permission, including any new one.
  • The chairman changes the treasurer's and other roles' permissions in "Roles".
  • A member without permissions sees only their own data — enforced by the server.

  • Payments: "View payments" (chairman, treasurer) opens "Payments", the cards, the allocation and the "Payments" report; "Enter payments" (chairman, treasurer) enters payments, splits them over plots, reallocates and allocates prepayment; "Reverse payments" (the chairman only) reverses a payment - a treasurer who made a mistake asks the chairman. The "Allocate prepayment automatically" switch needs "Manage settings". A member sees the payments of their own plots in "My charges"; the electrician sees none.
  • Documents: "Issue invoices" (chairman, treasurer) builds, re-issues and prints invoices; "Issue certificates" (the chairman only) issues and annuls certificates; invoices and the register of certificates are seen with "View charges", a cash receipt printed with "View payments". A member gets the invoices and receipts of their own plots only and never certificates.

8 Data, security, personal data

Isolation
Database RLS on every table with cooperative data; the application cannot bypass it.
Access
The server checks permissions on every request; a member sees only their own plots.
Audit log
Who, when, what changed, old and new value. Entries are never changed or deleted.
Not stored
Tax numbers (РНОКПП), passport data, dates of birth — there are no such fields.
Server logs
No personal data: even a database error message does not include values.
Events
Completed events are deleted from the event table at once, because they may carry personal data.
Secrets
Only from environment variables; the repository holds only local development passwords. CI scans for leaked secrets (gitleaks).
Report templates are data
The system never executes formulas or code from a template: placeholders are substituted, formulas are left alone, and Excel recalculates them in the opened file. Macros (.xlsm), active content, OLE objects and external links never reach storage (links are removed with a warning). Only .xlsx up to 2 MB is accepted; the zip-bomb guard (limits on the unpacked size and the compression ratio) and the XXE guard (XML without DTDs or external entities) apply both at upload and at every generation. Templates and versions are tables with tenant_id, RLS and isolation between cooperatives; generated files are not stored.
Reports and personal data
Personal data (names, phones, e-mails) is only in the "Debtors" report, which also needs "View members"; templates have none. The platform operator sees neither reports nor cooperative data. The audit log has the actions REPORT_GENERATED (the report or the template with its version, the filters, the row count — never the content), REPORT_TEMPLATE_UPLOADED and REPORT_TEMPLATE_ARCHIVED; a change of requisites is recorded with the changed fields.
Dependencies
CI checks known vulnerabilities (pnpm audit, OSV) and the code (Semgrep).
Encrypted contacts
Phones, email, postal address, Telegram, Viber and the notes of a member are stored encrypted (AES-256-GCM), also in the audit log and in the pending Excel import. Names stay readable, because the board searches and sorts by them. A copy of the database without the master key reveals no contact. On the server the disk and the backups are encrypted as well (chapter 9).

Personal data encryption: keys

  • Master key NADEL_PD_MASTER_KEY: 32 random bytes in base64. It lives only in the server's environment — never in the database, the repository, the logs or a backup.
  • Cooperative keys: every cooperative has its own data key (and a key for the search indexes), kept in the database wrapped by the master key. They are created the first time a cooperative needs them. So a stolen database holds only wrapped keys, and one cooperative's key never opens another's data.
  • Search finds contacts without decrypting the table: the server compares keyed hashes of the full phone, its last 4 digits and the whole email (chapter 6, "Members").

Generating the master key

openssl rand -base64 32

Put the output into the server's secret store as NADEL_PD_MASTER_KEY. Use different keys for staging and production. The server in the prod profile refuses to start without a key or with one that is not 32 bytes of base64; the message names the setting NADEL_PD_MASTER_KEY and never shows a key. With a key that does not match the database it refuses too, with PD_MASTER_KEY_MISMATCH (chapter 12).

A lost master key = lost contacts

Nothing else can open the encrypted contacts: not a backup, not the developers. Keep at least two copies offline (a password manager entry and a sealed paper copy), apart from the database backups. A backup stored together with its key gives no protection, and a backup without the key cannot be restored to readable contacts. Names, plots, charges and payments are not affected — only the contacts, addresses and notes.

Rotating the master key

  1. Generate a new key: openssl rand -base64 32.
  2. Deploy with the new key as NADEL_PD_MASTER_KEY and the old one as NADEL_PD_MASTER_KEY_PREVIOUS.
  3. At start-up the server re-wraps every cooperative's keys with the new key (one transaction per cooperative) and logs counts only, for example Personal data keys: 12 checked, 12 re-wrapped, 0 left on the previous master key. If a key is wrapped with neither master key, the start-up stops with PD_MASTER_KEY_MISMATCH before anything is changed.
  4. Remove NADEL_PD_MASTER_KEY_PREVIOUS and deploy again.
  5. Keep the old key offline until no backup made before the rotation is retained: such a backup still holds keys wrapped by the old key.

Only the master key is rotated; the cooperatives' own data keys stay as they are. Restore drills need the key: restore the database, start the backend with the key and check that contacts open.

9 Server deployment planned · 6a

The decision (ADR 0010): the whole product is finished locally first, the server comes last. The plan is as follows.

What runs on the server

  • One virtual server in an EU data centre (initially Hetzner Cloud, Germany or Finland), about 4 vCPU and 8 GB RAM; a smaller second one for staging.
  • Docker Compose: PostgreSQL + PostGIS, Keycloak in production mode, the backend and Caddy (the web client, HTTPS with automatic certificates). Only ports 80 and 443 are open to the outside.
  • Cost: tens of euros per month.

How updates arrive

  1. Every merge to main: GitHub builds the images, pushes them to the GitHub Container Registry and updates staging.
  2. A version tag v…: deployment to production after your approval in GitHub, with a database backup right before.
  3. Rollback: deploy the previous tag with a separate action.

First installation

  • The server: SSH keys only, no root, a firewall, automatic security updates.
  • A domain and DNS pointing to the server; secrets in the server's environment file and in GitHub environments; the backend refuses to start with a default password.
  • A "first cooperative" command creates the cooperative, its chairman and the Keycloak account and sends the set-your-password email.
  • The Keycloak admin console and the database only through an SSH tunnel.

Backups and monitoring

  • Every night an encrypted copy of the application and Keycloak databases, stored outside the server; 30 daily and 12 monthly copies kept. Every month a copy is restored on staging as a test.
  • An external uptime check with Telegram alerts; error tracking without personal data; disk, memory and certificate alerts.

A step-by-step runbook with exact commands joins this chapter with the deployment feature.

10 Updates and database migrations

  • The database structure changes only through Flyway migrations (backend/src/main/resources/db/migration), run when the backend starts. Existing migrations are never edited — only new ones are added.
  • "Expand, then contract": a release may add tables and fields; removing or renaming waits for the next release, when the old code no longer runs. The previous version thus works on the new database and a rollback is safe.
  • Demo data (db/demo) loads only in the development profile; the server never has it.

11 How the system is developed

From an idea to main

  1. A feature document in docs/features/NNN-….md: requirements, rules, worked examples, acceptance criteria. The number is the highest in context/spec + 1.
  2. The pipeline: /feature-pipeline docs/features/NNN-….md in Claude Code. Agents write the specification, the plan, the code and the tests slice by slice; a separate reviewer checks every slice; at the end every criterion is verified, screenshots taken, the full suite run, a PR opened and its checks brought to green.
  3. Your check: the app from the PR branch is running for you; try the scenarios from the report.
  4. Merging — only you: gh pr merge <number> --squash --delete-branch, then git switch main && git pull.

CI checks on every PR

Check What it does
Backend Build, every test with a database container, module boundaries, coverage floor
Clients API contract, formatting, types, tests, lint, web build
Security Leaked secrets (gitleaks), dependency vulnerabilities (pnpm audit, OSV)
SAST Static code analysis (Semgrep)
End-to-end Browser scenarios on a freshly started database

Rules

  • Agents never merge or approve PRs and never push to main; only the owner commits changes to CLAUDE.md and .claude/.
  • Commits never mention AI. All repository text is English, except the guides in docs/guide (Ukrainian and English).
  • Verification levels: a new feature runs the full suite locally; a small fix on an open PR runs only the affected tests, and CI runs the full suite.
  • Models: the orchestrator and the reviewer use your Claude Code session's model (Opus); the worker agents use the model set in .claude/agents.
  • Working notes outside git: NOTES.local.md (questions and answers) and DECISIONS.local.md (decisions and deferred tasks).

12 Common problems and fixes

Problem Cause and fix
"Port 8080 was already in use", the web opened on 5174 A previous run is still going (for example the one the pipeline left for review). lsof -ti :8080 -ti :5173 | xargs kill, then make up.
"Account not linked" The email in Keycloak differs from the member card's, or the member is archived, or Keycloak has no tenant_id.
admin cannot sign in to the Keycloak console Use the master realm at /admin/, not nadel; check the keyboard layout.
"E2E …" entries and odd plots in the audit log Traces of old end-to-end tests. Reset the local database (chapter 2); the tests now use a separate database.
"platform (linux/amd64) does not match" for postgres The default PostGIS image is Intel-only and runs emulated on a Mac — slower, tests included. Set NADEL_POSTGIS_IMAGE to the arm64 image (chapter 2) and reset the local database.
Slow backend tests, long CI On a Mac first check NADEL_POSTGIS_IMAGE (chapter 2): under emulation the suite takes several times longer. The time of every test class is in backend/target/surefire-reports.
Git: "File exists … .lock" A lock file left by an interrupted command. Make sure no git is running and delete the named .lock.
The backend does not start: PD_MASTER_KEY_MISMATCH in the log The server was started with a master key other than the one that wrapped the cooperatives' keys (a different environment's key, a lost or changed value). Start it with the right key. To change the master key on purpose, start with the new key as NADEL_PD_MASTER_KEY and the old one as NADEL_PD_MASTER_KEY_PREVIOUS (chapter 8, rotation). Locally: use the key in infra/.env, or, if that file was lost, reset the local database with docker compose -f infra/docker-compose.yml down -v (demo data only).
The backend does not start: NADEL_PD_MASTER_KEY is missing or is not 32 bytes of base64 The variable is not set or is malformed (extra characters, a truncated copy). Generate one with openssl rand -base64 32, or on a local run use make up / make backend, which create infra/.env (chapter 2). The same message names NADEL_PD_MASTER_KEY_PREVIOUS if that one is malformed.
Realm file changes did not apply The realm is imported only into an empty Keycloak — reset the local database.
IntelliJ keeps asking for access to other apps' data System Settings → Privacy & Security → Full Disk Access → IntelliJ IDEA, restart.
A generated Excel file opens with a repair prompt Tell the developer and attach the template and the generated file. The template filler is our own (ADR 0015); a repair message is one of the conditions for reconsidering it in favour of Apache POI.
The pipeline stopped /feature-pipeline resume continues where it stopped, from its log.
