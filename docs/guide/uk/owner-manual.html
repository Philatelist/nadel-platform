1 Як влаштована платформа

Одна платформа обслуговує багато кооперативів. Дані кожного кооперативу відокремлені самою базою даних.

Вебклієнт
Екрани правління й кабінет члена. Нічого не рахує, лише показує те, що віддає сервер.
Бекенд
Один застосунок (модульний моноліт) з модулями: tenancy (кооперативи), identity (вхід і дозволи), members, plots, settings, imports, tariffs, meters, money, audit. Межі модулів перевіряє тест.
Контракт API
Файл api/openapi.yaml — єдине джерело правди: з нього генеруються інтерфейси сервера й клієнт для вебу та застосунку.
PostgreSQL
Усі дані. Кожна таблиця з даними кооперативу має tenant_id і політику RLS: запит бачить лише рядки свого кооперативу.
Keycloak
Облікові записи, паролі, вхід. Ролі кооперативу в Keycloak не зберігаються — лише в базі; у Keycloak є тільки роль оператора платформи.
Мобільний застосунок
Каркас на Expo є; повноцінний застосунок — фаза 5.

Як проходить запит

  1. Людина входить через Keycloak і отримує токен з атрибутом tenant_id (її кооператив).
  2. Бекенд перевіряє токен, знаходить члена кооперативу за електронною поштою і бере його дозволи з бази.
  3. На час запиту база отримує tenant_id; RLS пропускає лише рядки цього кооперативу.
  4. Зміни, зроблені правлінням, публікуються як події; модуль журналу записує їх через «outbox» — подія не губиться, навіть якщо сервер перезапустився.

2 Локальне середовище

Docker Desktop, JDK 25, Node.js 22 і pnpm, Git, GitHub CLI (gh). Репозиторій: ~/IdeaProjects/nadel-platform.

make install        # залежності вебу й спільних пакетів

Пошта, Telegram і фонові завдання у розробці

Розсилка (функція 017) у локальному середовищі не виходить назовні: листи ловить Mailpit, а замість справжнього Telegram працює фальшивий сервер Bot API. Обидва запускає make infra (сервіси mailpit і fake-telegram у infra/docker-compose.yml).

  • Mailpit. SMTP — localhost:1025 (без шифрування, без пароля), вебсторінка й API — http://localhost:8025; curl localhost:8025/api/v1/messages показує листи. Листи живуть у пам’яті й зникають після перезапуску. Тут видно тестовий лист із «Розсилки» та рахунки з PDF у вкладенні.
  • Фальшивий Telegram (infra/fake-telegram/server.mjs, порт 8091) зберігає оновлення й надіслані бота повідомлення за токеном, тож боти двох кооперативів не змішуються. Токен, що починається на bad, отримує 401 (так перевіряють «Токен недійсний»). Керування: 
# член «натискає Почати» з кодом підключення (чат 555)
curl -s -X POST localhost:8091/control/updates -H 'content-type: application/json' \
  -d '{"token":"123:demo","chatId":555,"text":"/start ABC123","firstName":"Олена"}'

# що бот надіслав у чат 555 (метод, текст, назва файлу, кнопки, час)
curl -s 'localhost:8091/control/sent?token=123:demo&chatId=555'

# член заблокував бота (sendMessage відповідає 403) і зняти блокування
curl -s -X POST localhost:8091/control/block/555
curl -s -X DELETE localhost:8091/control/block/555

# забути все
curl -s -X POST localhost:8091/control/reset
  • Змінна NADEL_TELEGRAM_API_URL — адреса Bot API. У профілі dev за замовчуванням http://localhost:8091 (фальшивий сервер), в усіх інших — https://api.telegram.org. Для перевірки зі справжнім ботом задайте NADEL_TELEGRAM_API_URL=https://api.telegram.org, збережіть справжній токен у «Розсилці» демо-кооператива й зупиніть фальшивий сервіс (docker compose -f infra/docker-compose.yml stop fake-telegram). Змінну належить додати до .env.example — це робить власник перед злиттям; без неї діють значення за замовчуванням.
  • Демо-дані. Профіль dev наповнює демо-кооператив сам: скринька вказує на Mailpit (відправник board@demo.local), бот налаштовано на фальшивий Telegram (токен 123456:DEMO-fake-telegram-token, ім’я nadel_demo_bot), підключено двох членів (member@demo.local і Дмитра Кравченка), а рахунки закритого місяця вже «надіслано» (одна спроба) або «до друку». Нічого не ставиться в чергу, тож запуск не засипає Mailpit. Другий демо-кооператив лишається ненастроєним.
  • JobRunr будить роботу розсилки й відновлює її після збою. Його таблиці створює Flyway (міграція V30__jobrunr.sql, бо роль nadel_app не може створювати таблиці), панель керування вимкнено, дані про використання не надсилаються. Таблиці JobRunr, як і event_publication, без tenant_id та RLS: аргументи завдань — лише ідентифікатор кооперативу й канал.
  • Бот і довге опитування. Кожен бот кооперативу система сама опитує (getUpdates, 25 секунд), без публічної адреси й вебхуків. Опитує один екземпляр застосунку: він отримує «оренду» (рядок кооперативу в таблиці bot_poll_state, 60 секунд, за часом бази). Другий екземпляр чекає й підхоплює бота приблизно за хвилину, коли перший зупинився; чисте вимкнення віддає оренду одразу. Кожне оновлення береться «не більше разу»: після збою одна відповідь може загубитися (член просто натисне ще раз), але показання лічильника з бота ніколи не буде передано двічі. Якщо фальшивий сервер не запущено, застосунок працює, а бот повторює спробу з наростаючою паузою.

Локальний головний ключ (infra/.env)

Контакти членів зберігаються зашифрованими (розділ 8). Під час першого запуску make up, make backend або make e2e створюється файл infra/.env з одним рядком, NADEL_PD_MASTER_KEY=… — випадковим локальним ключем. Файл ігнорується git, має права 600 і читається лише процесом бекенду. Наявний файл ніколи не перезаписується.

  • Не комітьте цей файл і не вставляйте ключ у чат чи тікет.
  • Якщо його видалити, контакти, що вже є в локальній базі, стануть нечитабельними (бекенд не запуститься з PD_MASTER_KEY_MISMATCH, розділ 12). Тоді скиньте й локальну базу (нижче) — це лише демо-дані.

Скинути локальну базу

make down && docker compose -f infra/docker-compose.yml down -v && make up

Стирає всі локальні дані; міграції й демо-дані завантажуються заново, Keycloak знову імпортує realm. Потрібно, коли змінено infra/keycloak/nadel-realm.json або демо зіпсоване тестовими даними.

Образ PostGIS на Mac з Apple Silicon

Типовий образ postgis/postgis:17-3.5 існує лише для Intel (linux/amd64); на Mac із процесором M-серії Docker запускає його через емуляцію, і база, зокрема в тестах бекенду, працює в рази повільніше. Локальний стек і тести бекенду (Testcontainers) беруть образ зі змінної середовища NADEL_POSTGIS_IMAGE. На Mac додайте до профілю оболонки (~/.zshrc) мультиархітектурну збірку тих самих PostgreSQL 17 + PostGIS 3.5: 

export NADEL_POSTGIS_IMAGE=imresamu/postgis:17-3.5

Її збирає один із супровідників офіційних образів PostGIS з тих самих вихідних кодів. Після перемикання один раз скиньте локальну базу (вище): том із даними не переноситься між архітектурами процесора. CI і сервери лишаються на типовому образі.

3 Keycloak: входи й облікові записи

Keycloak зберігає облікові записи й паролі. Realm (простір) платформи — nadel; у ньому два клієнти: nadel-web і nadel-mobile. Вхід — за електронною поштою, самостійна реєстрація вимкнена, скидання пароля поштою дозволене (запрацює, коли буде налаштовано пошту), мови сторінки входу — українська (за замовчуванням) і англійська.

Як обліковий запис пов’язаний із кооперативом

  • Атрибут користувача tenant_id — ідентифікатор кооперативу. Він потрапляє в токен, і бекенд працює лише з даними цього кооперативу.
  • Член кооперативу знаходиться за електронною поштою: пошта в Keycloak має збігатися з поштою в картці члена (регістр літер неважливий). Під час першого входу бекенд запам’ятовує зв’язок. Першого голову нового кооперативу зв’язують інакше — за ідентифікатором користувача Keycloak (розділ 4).
  • Ролі й дозволи — у базі кооперативу, не в Keycloak. Виняток — роль PLATFORM_OPERATOR.

Створити обліковий запис для члена кооперативу

  1. Переконайтеся, що член є в системі й у його картці вказано електронну пошту (це робить голова кооперативу).
  2. Адмін-консоль Keycloak → угорі ліворуч оберіть realm nadel → Users → Add user.
  3. Username і Email — та сама пошта; First name, Last name; увімкніть Email verified; Create.
  4. Вкладка Attributes: ключ tenant_id, значення — ідентифікатор кооперативу (розділ 4) → Save.
  5. Вкладка Credentials → Set password: тимчасовий пароль з увімкненим Temporary — під час першого входу людина задасть свій.
Якщо немає вкладки Attributes

У Keycloak 26 довільні атрибути за замовчуванням приховані. Один раз: Realm settings → General → Unmanaged attributes → «Admin can edit» → Save.

4 Кооперативи: створення й ізоляція

Кооператив (у коді — tenant) — запис у таблиці tenant з ідентифікатором (UUID) і назвою. Під час створення кооперативу система додає йому базові ролі, налаштування й стандартні види нарахувань.

Створити новий кооператив (до появи консолі оператора)

Контакти (телефони, пошту, адресу) шифрує застосунок, тому записати їх через SQL не можна. Першого голову створюють без контактів і пов’язують з обліковим записом Keycloak за його ідентифікатором; пошту й телефони голова вносить у застосунку потім.

  1. Підключіться до бази як суперкористувач: docker compose -f infra/docker-compose.yml exec postgres psql -U postgres -d nadel.
  2. Створіть кооператив, підставивши назву, і запам’ятайте ідентифікатор з повідомлення:
DO $$
DECLARE t uuid := gen_random_uuid();
BEGIN
  INSERT INTO tenant (id, name) VALUES (t, 'СТ «Назва»');
  PERFORM seed_base_roles(t);          -- ролі, налаштування, види нарахувань
  RAISE NOTICE 'tenant_id = %', t;
END $$;
  1. Створіть голові обліковий запис у Keycloak з атрибутом tenant_id цього ідентифікатора (розділ 3). Відкрийте нового користувача й скопіюйте ID з вкладки Details (UUID) — це subject у Keycloak.
  2. Поверніться до psql і додайте голову з ідентифікатором та subject (підставте прізвище, ім’я й обидва значення): 
DO $$
DECLARE t uuid := '<tenant_id>'; m uuid := gen_random_uuid();
BEGIN
  INSERT INTO member (id, tenant_id, last_name, first_name, delivery_channel, keycloak_subject)
  VALUES (m, t, 'Прізвище', 'Ім’я', 'PAPER', '<ID користувача Keycloak>');
  INSERT INTO member_role (tenant_id, member_id, role_id)
  SELECT t, m, id FROM role WHERE tenant_id = t AND base_code = 'CHAIRMAN';
END $$;
  1. Голова входить (subject пов’язує обліковий запис із карткою), відкриває «Члени» → власну картку → «Редагувати» і вносить пошту, телефони та бажаний канал; застосунок їх шифрує. Далі — імпорт з Excel, члени, тарифи, лічильники.

Ключі шифрування кооперативу сервер створює сам, коли вони вперше знадобляться (наприклад, коли голова збереже перший контакт); тут робити для цього нічого не потрібно. Канал доставки лишається «Папір», доки немає контакту, бо база відхиляє канал без його контакту.

Тимчасовий спосіб

Цей SQL — обхідний шлях до появи консолі оператора; створення через нього не потрапляє в журнал змін. На сервері його замінить окрема команда «перший кооператив» (розділ 9), а згодом — консоль оператора.

Ізоляція

  • Застосунок працює з базою під роллю nadel_app без права обходити RLS; міграції виконує nadel_owner.
  • Для кожної нової таблиці є тест ізоляції: дані іншого кооперативу не видно навіть прямим запитом.
  • Видалення кооперативу не передбачене; дані зберігаються, доки не буде рішення про архівування (фаза 7).

Документи: реквізити, шрифти, рушій PDF

  • Реквізити. IBAN, назву, адресу й банк вносить голова в налаштуваннях. Код ЄДРПОУ належить власному запису кооперативу, і задає його лише оператор платформи; доки немає консолі оператора, власник вписує його в колонку edrpou рядка кооперативу в таблиці tenant від імені власника бази даних. Без обох реквізитів рахунки не формуються.
  • Мова. Документи завжди українською, якою б мовою не були екрани користувача: це офіційні документи. Мову, яку обрав користувач, мають лише екрани.
  • Шрифти. У PDF вбудовано підмножину IBM Plex Sans (шрифт дизайну застосунку) за ліцензією SIL Open Font License 1.1. Файли шрифту й текст ліцензії лежать у ресурсах бекенду й мають іти разом. Кирилицю та знак гривні видно без жодних шрифтів на комп’ютері читача.
  • Рушій PDF — Apache PDFBox. PDF не зберігається: його малюють щоразу з даних, що збережено під час формування, і та сама версія завжди дає той самий файл (окрім технічної дати створення). Зображення QR-коду робить ZXing; розкладка відповідає правилам Національного банку України (формат 003).
  • Ліміт формування. Рахунки місяця формуються одним запитом, поки казначей чекає. Виміряний ліміт для найбільшого підтримуваного кооперативу: див. ADR 0017 (docs/adr/0017-documents.md).
  • Дозволи. «Формування рахунків» (за замовчуванням голова й казначей) формує, перевипускає й друкує рахунки; «Видача довідок» (голова) видає й анулює довідки. Для перегляду потрібен «Перегляд нарахувань», для друку квитанції — «Перегляд платежів». Обидва дозволи можна дати власній ролі на екрані ролей.

8 Дані, безпека, персональні дані

Ізоляція
RLS у базі для кожної таблиці з даними кооперативу; застосунок не може її обійти.
Доступ
Дозволи перевіряє сервер на кожному запиті; член бачить лише свої ділянки.
Журнал змін
Хто, коли, що змінив, старе й нове значення. Записи не змінюються й не видаляються.
Не зберігається
РНОКПП, паспортні дані, дати народження — окремих полів немає.
Логи сервера
Без персональних даних: навіть текст помилки бази з’єднання не показує значень.
Події
Виконані події одразу видаляються з таблиці подій, бо можуть містити персональні дані.
Секрети
Лише зі змінних середовища; у репозиторії — тільки паролі для локальної розробки. Перевірку на витоки секретів робить CI (gitleaks).
Шаблони звітів — це дані
Система ніколи не виконує формул чи коду з шаблону: поля підставляються, формули лишаються, а Excel перераховує їх у відкритому файлі. Макроси (.xlsm), активний вміст, OLE-об’єкти й зовнішні посилання до сховища не потрапляють (посилання прибираються з попередженням). Файл — лише .xlsx до 2 МБ; захист від zip-бомб (обмеження розпакованого розміру й стиснення) і від XXE (XML без DTD та зовнішніх сутностей) діє і при завантаженні, і при кожному формуванні. Шаблони й версії — таблиці з tenant_id, RLS та ізоляцією між кооперативами; згенеровані файли не зберігаються.
Звіти й персональні дані
Персональні дані (імена, телефони, ел. пошта) є лише у звіті «Боржники», який потребує ще й «Перегляд членів»; у шаблонах їх немає. Оператор платформи звітів і даних кооперативів не бачить. Журнал змін містить дії REPORT_GENERATED (звіт чи шаблон із версією, фільтри, кількість рядків — без вмісту), REPORT_TEMPLATE_UPLOADED і REPORT_TEMPLATE_ARCHIVED; зміни реквізитів записуються зі зміненими полями.
Секрети кооперативу: єдиний виняток
Пароль поштової скриньки й токен бота належать кооперативу, і їх вводить правління, тож вони — дані кооператива, а не змінні середовища (ADR 0018). Їх запечатано ключем самого кооператива (AES-256-GCM, головний ключ — із середовища), вони недоступні для читання через API («збережено» й останні 4 символи токена) і ніколи не потрапляють у журнал змін, події чи логи. Секрети самої платформи (база, головний ключ, Keycloak) лишаються тільки у змінних середовища. Оператор платформи скриньок і ботів кооперативів не бачить. Втрата головного ключа означає, що голова вводить пароль і токен заново.
Дві функції між кооперативами
Опитувач ботів і щохвилинний огляд черги мусять знати, у яких кооперативів є бот чи повідомлення, ще не маючи поточного кооператива. Для цього існують дві функції бази (notifications_bot_tenants() і notifications_due_lanes()): вони повертають лише ідентифікатори кооперативів і код каналу, ніколи рядка, адреси чи тексту; виконувати їх може лише nadel_app. Це єдині функції платформи, що перетинають кооперативи; кожне читання даних далі йде вже в межах свого кооператива під RLS. Нова така функція потребує окремого ADR.
Куди йдуть листи
Адресу поштового сервера вводить голова, і тестовий лист з’єднується з нею з сервера. Це свідомо прийняте обмеження (ADR 0018): дозвіл «Керування налаштуваннями» є лише в голови, з’єднання має 10-секундні тайм-аути, а відповідь містить лише код і останній рядок відповіді сервера.
Залежності
CI перевіряє відомі вразливості (pnpm audit, OSV) і код (Semgrep).
Зашифровані контакти
Телефони, пошта, поштова адреса, Telegram, Viber і примітки члена зберігаються зашифрованими (AES-256-GCM), також у журналі змін і в очікуваному імпорті з Excel. Імена лишаються читабельними, бо правління шукає й сортує за ними. Копія бази без головного ключа не розкриває жодного контакту. На сервері додатково шифруються диск і резервні копії (розділ 9).

Шифрування персональних даних: ключі

  • Головний ключ NADEL_PD_MASTER_KEY: 32 випадкові байти в base64. Він живе лише в середовищі сервера — ніколи в базі, репозиторії, логах чи резервній копії.
  • Ключі кооперативів: кожен кооператив має власний ключ даних (і ключ для індексів пошуку), які зберігаються в базі обгорнутими головним ключем. Їх створюють, коли кооперативу вперше знадобляться. Тож викрадена база містить лише обгорнуті ключі, а ключ одного кооперативу ніколи не відкриє даних іншого.
  • Пошук знаходить контакти, не розшифровуючи таблицю: сервер порівнює ключові геші повного телефону, його останніх 4 цифр і повної пошти (розділ 6, «Члени»).

Згенерувати головний ключ

openssl rand -base64 32

Результат покладіть у сховище секретів сервера як NADEL_PD_MASTER_KEY. Для staging і production використовуйте різні ключі. Сервер у профілі prod не запускається без ключа або з ключем, що не є 32 байтами base64; повідомлення називає змінну NADEL_PD_MASTER_KEY і ніколи не показує ключа. З ключем, що не збігається з базою, він теж не запускається — з кодом PD_MASTER_KEY_MISMATCH (розділ 12).

Втрачений головний ключ = втрачені контакти

Зашифровані контакти не відкриє ніщо інше: ні резервна копія, ні розробники. Тримайте щонайменше дві копії офлайн (запис у менеджері паролів і запечатану паперову копію) окремо від резервних копій бази. Копія, що лежить разом зі своїм ключем, не захищає, а копія без ключа не відновлюється до читабельних контактів. Імена, ділянки, нарахування й платежі не страждають — лише контакти, адреси й примітки.

Змінити головний ключ (ротація)

  1. Згенеруйте новий ключ: openssl rand -base64 32.
  2. Розгорніть з новим ключем як NADEL_PD_MASTER_KEY і старим як NADEL_PD_MASTER_KEY_PREVIOUS.
  3. Під час запуску сервер перезгортає ключі кожного кооперативу новим ключем (одна транзакція на кооператив) і пише в лог лише кількості, наприклад Personal data keys: 12 checked, 12 re-wrapped, 0 left on the previous master key. Якщо якийсь ключ обгорнутий жодним із двох головних ключів, запуск зупиняється з PD_MASTER_KEY_MISMATCH до будь-яких змін.
  4. Приберіть NADEL_PD_MASTER_KEY_PREVIOUS і розгорніть знову.
  5. Тримайте старий ключ офлайн, доки зберігається хоч одна резервна копія, зроблена до ротації: вона досі містить ключі, обгорнуті старим ключем.

Змінюється лише головний ключ; власні ключі даних кооперативів лишаються. Тренування відновлення потребують ключа: відновіть базу, запустіть бекенд з ключем і перевірте, що контакти відкриваються.

9 Розгортання на сервері планується · 6а

Рішення (ADR 0010): спочатку весь продукт готовий локально, сервер — наприкінці. План такий.

Що буде на сервері

  • Один віртуальний сервер у дата-центрі ЄС (спочатку Hetzner Cloud, Німеччина чи Фінляндія), близько 4 vCPU і 8 ГБ пам’яті; менший другий — тестовий (staging).
  • Docker Compose: PostgreSQL + PostGIS, Keycloak у робочому режимі, бекенд і Caddy (вебклієнт, HTTPS з автоматичними сертифікатами). Назовні відкриті лише порти 80 і 443.
  • Вартість — десятки євро на місяць.

Як потраплятимуть оновлення

  1. Кожне злиття в main: GitHub збирає образи, кладе їх у GitHub Container Registry і оновлює staging.
  2. Тег версії v…: розгортання на робочий сервер після вашого підтвердження в GitHub; перед цим — резервна копія бази.
  3. Відкат — розгорнути попередній тег окремою дією.

Перший запуск

  • Сервер: вхід лише за SSH-ключем, без root, брандмауер, автоматичні оновлення безпеки.
  • Домен і DNS на сервер; секрети — у файлі середовища на сервері й у середовищах GitHub; із паролями «за замовчуванням» бекенд не стартує.
  • Команда «перший кооператив» створює кооператив, голову й обліковий запис у Keycloak та надсилає лист для встановлення пароля.
  • Адмін-консоль Keycloak і база — лише через SSH-тунель.

Резервні копії й нагляд

  • Щоночі зашифрована копія бази застосунку й Keycloak — поза сервером; зберігаються 30 щоденних і 12 щомісячних. Щомісяця копію відновлюють на staging для перевірки.
  • Зовнішня перевірка доступності з повідомленням у Telegram; відстеження помилок без персональних даних; попередження про диск, пам’ять і сертифікат.

Покроковий порядок дій із точними командами з’явиться в цьому розділі разом із фічею розгортання.

10 Оновлення й міграції бази

  • Структура бази змінюється лише міграціями Flyway (backend/src/main/resources/db/migration); вони виконуються під час старту бекенду. Наявні міграції ніколи не редагуються — лише додаються нові.
  • Правило «розширити, потім звузити»: реліз може додати таблиці й поля; видалення чи перейменування — у наступному релізі, коли старий код уже не працює. Так попередня версія працює на новій базі, і відкат безпечний.
  • Демо-дані (db/demo) завантажуються лише в профілі розробки; на сервері їх не буде.

11 Як розробляється система

Від ідеї до main

  1. Документ фічі в docs/features/NNN-….md: вимоги, правила, розібрані приклади, критерії приймання. Номер = найбільший у context/spec + 1.
  2. Конвеєр: /feature-pipeline docs/features/NNN-….md у Claude Code. Агенти пишуть специфікацію, план, код і тести зріз за зрізом; кожен зріз перевіряє окремий рецензент; наприкінці — перевірка всіх критеріїв, знімки, повний набір тестів, відкриття PR і очікування зелених перевірок.
  3. Ваша перевірка: застосунок із гілки PR запущено для вас; спробуйте сценарії зі звіту.
  4. Злиття — лише ви: gh pr merge <номер> --squash --delete-branch, потім git switch main && git pull.

Перевірки CI на кожному PR

Перевірка Що робить
Backend Збирання, усі тести з контейнером бази, межі модулів, мінімальне покриття
Clients Контракт API, форматування, типи, тести, лінтер, збирання вебу

Правила

  • Агенти ніколи не зливають PR, не схвалюють їх і не пушать у main; зміни в CLAUDE.md і .claude/ комітить лише власник.
  • У комітах немає згадок про ШІ. Увесь текст у репозиторії англійською, крім посібників docs/guide (українська й англійська).
  • Рівні перевірки: нова фіча — повний прогін локально; дрібне виправлення відкритого PR — лише зачеплені тести, повний прогін робить CI.
  • Моделі: оркестратор і рецензент — модель вашої сесії Claude Code (Opus); агенти-виконавці — як указано в .claude/agents.
  • Робочі нотатки поза git: NOTES.local.md (питання й відповіді) і DECISIONS.local.md (рішення й відкладені задачі).

12 Типові проблеми й рішення

Проблема Причина й рішення
«Port 8080 was already in use», веб відкрився на 5174 Працює попередній запуск (наприклад, залишений конвеєром для перевірки). lsof -ti :8080 -ti :5173 | xargs kill, потім make up.
«Обліковий запис не прив’язано» Пошта в Keycloak не збігається з поштою в картці члена, або член в архіві, або в Keycloak немає tenant_id.
Не входить admin в адмін-консоль Keycloak Входьте в realm master за адресою /admin/, а не в nadel; перевірте розкладку клавіатури.
У журналі змін «E2E …» та дивні ділянки Сліди старих наскрізних тестів. Скиньте локальну базу (розділ 2); тепер тести працюють на окремій базі.
Попередження «platform (linux/amd64) does not match» для postgres Типовий образ PostGIS лише для Intel, на Mac працює через емуляцію — повільніше, зокрема тести. Задайте NADEL_POSTGIS_IMAGE з arm64-образом (розділ 2) і скиньте локальну базу.
Повільні тести бекенду, CI довго На Mac спершу перевірте NADEL_POSTGIS_IMAGE (розділ 2): з емуляцією набір тестів іде в рази довше. Час кожного класу тестів — у backend/target/surefire-reports.
Git: «File exists … .lock» Залишився файл блокування після перерваної команди. Переконайтеся, що git не працює, і видаліть указаний .lock.
Бекенд не запускається: у логу PD_MASTER_KEY_MISMATCH Сервер запущено з головним ключем, не тим, яким обгорнуто ключі кооперативів (ключ іншого середовища, втрачене чи змінене значення). Запустіть із правильним ключем. Щоб змінити головний ключ навмисно, запустіть з новим як NADEL_PD_MASTER_KEY і зі старим як NADEL_PD_MASTER_KEY_PREVIOUS (розділ 8, ротація). Локально: використайте ключ з infra/.env або, якщо цей файл втрачено, скиньте локальну базу командою docker compose -f infra/docker-compose.yml down -v (там лише демо-дані).
Бекенд не запускається: NADEL_PD_MASTER_KEY is missing or is not 32 bytes of base64 Змінну не задано або її значення некоректне (зайві символи, обрізана копія). Згенеруйте ключ командою openssl rand -base64 32, а на локальному запуску скористайтеся make up / make backend, які створюють infra/.env (розділ 2). Те саме повідомлення називає NADEL_PD_MASTER_KEY_PREVIOUS, якщо некоректна саме ця змінна.
Зміни в realm-файлі не застосувалися Realm імпортується лише в порожній Keycloak — скиньте локальну базу.
IntelliJ постійно просить доступ до даних інших програм Системні параметри → Конфіденційність і безпека → Повний доступ до диска → IntelliJ IDEA, перезапуск.
Згенерований файл Excel відкривається із запитом на відновлення Повідомте розробника й додайте шаблон та згенерований файл. Заповнювач шаблонів — власний (ADR 0015); повідомлення про відновлення — одна з умов, за яких рішення переглядають на користь Apache POI.
«Токен недійсний» у «Розсилці» або бот перестав відповідати Токен введено з помилкою, бота видалено чи токен перевипущено в @BotFather. Telegram відповідає 401, і система зупиняє бота кооператива, доки токен не змінять. Скопіюйте токен з @BotFather заново, збережіть його в «Розсилці» й натисніть «Перевірити бота»; бот запрацює приблизно за хвилину. Локально «bad…» навмисно дає цю помилку.
Бот мовчить, хоча токен правильний Бота опитує один екземпляр: якщо працювало два, другий підхопить його приблизно за хвилину після зупинки першого — зачекайте. Локально перевірте, що працює fake-telegram (docker compose -f infra/docker-compose.yml ps), що NADEL_TELEGRAM_API_URL вказує на нього (у dev типово так) і що токен демо-кооператива не справжній, коли адреса фальшива (і навпаки). Telegram недоступний — бот повторює спробу з паузою, застосунок не падає.
«Неправильний логін або пароль пошти» (SMTP_AUTH_FAILED) Звичайний пароль замість пароля застосунку, не ввімкнено двоетапну перевірку (Gmail) або доступ для поштових програм (Ukr.net), пароль застосунку відкликано, чи скриньку заблоковано сервісом через підозрілу активність. Створіть новий пароль застосунку, збережіть його, надішліть тестовий лист і натисніть «Надіслати ще раз» біля невдалих рядків. Повторів автоматично немає, бо пароль не підходить.
«Сервер пошти відмовив» (SMTP_REJECTED) на багатьох листах Безкоштовна скринька дійшла до добового ліміту чи відмовляє за надто швидку розсилку. Система повторює двічі (одразу, через 1 і 5 хвилин); якщо не минає, зменште «Листів на секунду» (типово 1), зачекайте до наступної доби й надішліть ще раз. Один рядок з відмовою — часто недійсна адреса одержувача.
Telegram відповідає «забагато запитів» (429) Нічого робити не треба: рядок переноситься на час, який вказав Telegram, спроба не витрачається, а лінія відправки на цей час зупиняється. Система сама тримає швидкість нижче за ліміти Telegram.
Локально не видно листів Відкрийте http://localhost:8025; листи в пам’яті Mailpit і зникають після перезапуску контейнера. Перевірте, що «Розсилка» демо-кооператива вказує на localhost:1025.

27.10.2026 Звіти не вводять нових правил, а шаблони — це дані (ADR 0015): власний потоковий заповнювач OOXML замість Apache POI (POI лишається записаним запасним варіантом; розмір рушія — близько 1900 рядків проти порогу 2000 для перегляду), без обчислення формул, макросів і зовнішніх посилань.
28.10.2026 Платежі (015): розподіл від найстарішого боргу, на один день — за порядком видів нарахувань; аванс автоматично йде на нові нарахування (налаштування, типово ввімкнено); внесення готівки має внутрішню квитанцію з наскрізним номером, а не фіскальний чек; сторнувати платіж може лише голова; платіж одного платника на кілька ділянок розділяє казначей під час внесення.
28.10.2026 Документи (016, ADR 0017): PDF малює Apache PDFBox із вбудованим IBM Plex Sans, вони завжди українською й ніколи не зберігаються (щоразу будуються з даних, що збережено); QR-код — формат НБУ 003 і ZXing; рахунки місяця формуються, поки казначей чекає, без черги завдань (JobRunr з’явиться з доставкою, функція 017); код ЄДРПОУ задає оператор платформи; два нові дозволи — «Формування рахунків» і «Видача довідок».
29.10.2026 Розсилка (017, ADR 0018): листи йдуть із власної поштової скриньки кооператива, а Telegram — через його власного бота (без спільного платформного бота й поштового сервісу); їхні секрети лежать у даних кооператива, запечатані його ключем (єдиний виняток із «секрети лише в середовищі»); бот працює через довге опитування з орендою на екземпляр, без вебхуків; дві функції бази, що перетинають кооперативи, повертають лише ідентифікатори; відправка — реєстр доставок, який опрацьовує JobRunr (три спроби, швидкість у пам’яті); новий дозвіл «Надсилання оголошень».
