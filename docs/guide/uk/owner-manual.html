1 Як влаштована платформа

Одна платформа обслуговує багато кооперативів. Дані кожного кооперативу відокремлені самою базою даних.

Вебклієнт
Екрани правління й кабінет члена. Нічого не рахує, лише показує те, що віддає сервер.
Бекенд
Один застосунок (модульний моноліт) з модулями: tenancy (кооперативи), identity (вхід і дозволи), members, plots, settings, imports, tariffs, meters, money, audit. Межі модулів перевіряє тест.
Контракт API
Файл api/openapi.yaml — єдине джерело правди: з нього генеруються інтерфейси сервера й клієнт для вебу та застосунку.
PostgreSQL
Усі дані. Кожна таблиця з даними кооперативу має tenant_id і політику RLS: запит бачить лише рядки свого кооперативу.
Keycloak
Облікові записи, паролі, вхід. Ролі кооперативу в Keycloak не зберігаються — лише в базі; у Keycloak є тільки роль оператора платформи.
Мобільний застосунок
Каркас на Expo є; повноцінний застосунок — фаза 5.

Як проходить запит

  1. Людина входить через Keycloak і отримує токен з атрибутом tenant_id (її кооператив).
  2. Бекенд перевіряє токен, знаходить члена кооперативу за електронною поштою і бере його дозволи з бази.
  3. На час запиту база отримує tenant_id; RLS пропускає лише рядки цього кооперативу.
  4. Зміни, зроблені правлінням, публікуються як події; модуль журналу записує їх через «outbox» — подія не губиться, навіть якщо сервер перезапустився.

2 Локальне середовище

Що потрібно на комп’ютері

Docker Desktop, JDK 25, Node.js 22 і pnpm, Git, GitHub CLI (gh). Репозиторій: ~/IdeaProjects/nadel-platform.

Перший запуск

make install        # залежності вебу й спільних пакетів
make up             # база, Keycloak, бекенд і веб в одному терміналі (Ctrl+C зупиняє бекенд і веб)
make e2e-install    # один раз: браузер для наскрізних тестів

3 Keycloak: входи й облікові записи

Keycloak зберігає облікові записи й паролі. Realm (простір) платформи — nadel; у ньому два клієнти: nadel-web і nadel-mobile. Вхід — за електронною поштою, самостійна реєстрація вимкнена, скидання пароля поштою дозволене (запрацює, коли буде налаштовано пошту), мови сторінки входу — українська (за замовчуванням) і англійська.

Як обліковий запис пов’язаний із кооперативом

  • Атрибут користувача tenant_id — ідентифікатор кооперативу. Він потрапляє в токен, і бекенд працює лише з даними цього кооперативу.
  • Член кооперативу знаходиться за електронною поштою: пошта в Keycloak має збігатися з поштою в картці члена. Під час першого входу бекенд запам’ятовує зв’язок.
  • Ролі й дозволи — у базі кооперативу, не в Keycloak. Виняток — роль PLATFORM_OPERATOR.

Створити обліковий запис для члена кооперативу

  1. Переконайтеся, що член є в системі й у його картці вказано електронну пошту (це робить голова кооперативу).
  2. Адмін-консоль Keycloak → угорі ліворуч оберіть realm nadel → Users → Add user.
  3. Username і Email — та сама пошта; First name, Last name; увімкніть Email verified; Create.
  4. Вкладка Attributes: ключ tenant_id, значення — ідентифікатор кооперативу (розділ 4) → Save.
  5. Вкладка Credentials → Set password: тимчасовий пароль з увімкненим Temporary — під час першого входу людина задасть свій.
Якщо немає вкладки Attributes

У Keycloak 26 довільні атрибути за замовчуванням приховані. Один раз: Realm settings → General → Unmanaged attributes → «Admin can edit» → Save.

Завдання Де

4 Кооперативи: створення й ізоляція

Кооператив (у коді — tenant) — запис у таблиці tenant з ідентифікатором (UUID) і назвою. Під час створення кооперативу система додає йому базові ролі, налаштування й стандартні види нарахувань.

Створити новий кооператив (до появи консолі оператора)

  1. Підключіться до бази як суперкористувач: docker compose -f infra/docker-compose.yml exec postgres psql -U postgres -d nadel.
  2. Виконайте, підставивши назву й дані голови:
DO $$
DECLARE t uuid := gen_random_uuid(); m uuid := gen_random_uuid();
BEGIN
  INSERT INTO tenant (id, name) VALUES (t, 'СТ «Назва»');
  PERFORM seed_base_roles(t);          -- ролі, налаштування, види нарахувань
  INSERT INTO member (id, tenant_id, last_name, first_name, email, delivery_channel)
  VALUES (m, t, 'Прізвище', 'Ім’я', 'holova@example.com', 'EMAIL');
  INSERT INTO member_role (tenant_id, member_id, role_id)
  SELECT t, m, id FROM role WHERE tenant_id = t AND base_code = 'CHAIRMAN';
  RAISE NOTICE 'tenant_id = %', t;
END $$;
  1. Запам’ятайте tenant_id з повідомлення й створіть голові обліковий запис у Keycloak з цим атрибутом (розділ 3).
  2. Голова входить і далі сам заповнює кооператив: імпорт з Excel, члени, тарифи, лічильники.
Тимчасовий спосіб

Цей SQL — обхідний шлях до появи консолі оператора; створення через нього не потрапляє в журнал змін. На сервері його замінить окрема команда «перший кооператив» (розділ 9), а згодом — консоль оператора.

Ізоляція

  • Застосунок працює з базою під роллю nadel_app без права обходити RLS; міграції виконує nadel_owner.
  • Для кожної нової таблиці є тест ізоляції: дані іншого кооперативу не видно навіть прямим запитом.
  • Видалення кооперативу не передбачене; дані зберігаються, доки не буде рішення про архівування (фаза 7).

5 Оператор платформи частково

Оператор — людина, що обслуговує платформу (ви). Принцип (ADR 0008): оператор не бачить даних кооперативів — ні членів, ні ділянок, ні грошей.

Що Стан
Вхід під operator@nadel.local: застосунок показує «Немає кооперативу», дані недоступні працює
Консоль оператора: список кооперативів, створення кооперативу й голови, блокування фаза 7
Звіти платформи без персональних даних: кількість кооперативів, ділянок, активних користувачів, обсяг сховища, стан підписки фаза 7
Доступ підтримки: голова дає тимчасовий доступ до свого кооперативу; кожна дія записується в його журнал фаза 7
Підписки й оплата за користування платформою фаза 7

Технічні завдання оператора до того: Keycloak (розділ 3), створення кооперативів (розділ 4), сервер і резервні копії (розділ 9).

9 Розгортання на сервері планується · 6а

Рішення (ADR 0010): спочатку весь продукт готовий локально, сервер — наприкінці. План такий.

Що буде на сервері

  • Один віртуальний сервер у дата-центрі ЄС (спочатку Hetzner Cloud, Німеччина чи Фінляндія), близько 4 vCPU і 8 ГБ пам’яті; менший другий — тестовий (staging).
  • Docker Compose: PostgreSQL + PostGIS, Keycloak у робочому режимі, бекенд і Caddy (вебклієнт, HTTPS з автоматичними сертифікатами). Назовні відкриті лише порти 80 і 443.
  • Вартість — десятки євро на місяць.

Як потраплятимуть оновлення

  1. Кожне злиття в main: GitHub збирає образи, кладе їх у GitHub Container Registry і оновлює staging.
  2. Тег версії v…: розгортання на робочий сервер після вашого підтвердження в GitHub; перед цим — резервна копія бази.
  3. Відкат — розгорнути попередній тег окремою дією.

Перший запуск

  • Сервер: вхід лише за SSH-ключем, без root, брандмауер, автоматичні оновлення безпеки.
  • Домен і DNS на сервер; секрети — у файлі середовища на сервері й у середовищах GitHub; із паролями «за замовчуванням» бекенд не стартує.
  • Команда «перший кооператив» створює кооператив, голову й обліковий запис у Keycloak та надсилає лист для встановлення пароля.
  • Адмін-консоль Keycloak і база — лише через SSH-тунель.

Резервні копії й нагляд

  • Щоночі зашифрована копія бази застосунку й Keycloak — поза сервером; зберігаються 30 щоденних і 12 щомісячних. Щомісяця копію відновлюють на staging для перевірки.
  • Зовнішня перевірка доступності з повідомленням у Telegram; відстеження помилок без персональних даних; попередження про диск, пам’ять і сертифікат.

Покроковий порядок дій із точними командами з’явиться в цьому розділі разом із фічею розгортання.

10 Оновлення й міграції бази

  • Структура бази змінюється лише міграціями Flyway (backend/src/main/resources/db/migration); вони виконуються під час старту бекенду. Наявні міграції ніколи не редагуються — лише додаються нові.
  • Правило «розширити, потім звузити»: реліз може додати таблиці й поля; видалення чи перейменування — у наступному релізі, коли старий код уже не працює. Так попередня версія працює на новій базі, і відкат безпечний.
  • Демо-дані (db/demo) завантажуються лише в профілі розробки; на сервері їх не буде.

11 Як розробляється система

Від ідеї до main

  1. Документ фічі в docs/features/NNN-….md: вимоги, правила, розібрані приклади, критерії приймання. Номер = найбільший у context/spec + 1.
  2. Конвеєр: /feature-pipeline docs/features/NNN-….md у Claude Code. Агенти пишуть специфікацію, план, код і тести зріз за зрізом; кожен зріз перевіряє окремий рецензент; наприкінці — перевірка всіх критеріїв, знімки, повний набір тестів, відкриття PR і очікування зелених перевірок.
  3. Ваша перевірка: застосунок із гілки PR запущено для вас; спробуйте сценарії зі звіту.
  4. Злиття — лише ви: gh pr merge <номер> --squash --delete-branch, потім git switch main && git pull.

Перевірки CI на кожному PR

Перевірка Що робить
Backend Збирання, усі тести з контейнером бази, межі модулів, мінімальне покриття
Clients Контракт API, форматування, типи, тести, лінтер, збирання вебу
Security Витоки секретів (gitleaks), вразливості залежностей (pnpm audit, OSV)
SAST Статичний аналіз коду (Semgrep)
End-to-end Сценарії в браузері на щойно піднятій базі

Правила

  • Агенти ніколи не зливають PR, не схвалюють їх і не пушать у main; зміни в CLAUDE.md і .claude/ комітить лише власник.
  • У комітах немає згадок про ШІ. Увесь текст у репозиторії англійською, крім посібників docs/guide (українська й англійська).
  • Рівні перевірки: нова фіча — повний прогін локально; дрібне виправлення відкритого PR — лише зачеплені тести, повний прогін робить CI.
  • Моделі: оркестратор і рецензент — модель вашої сесії Claude Code (Opus); агенти-виконавці — як указано в .claude/agents.
  • Робочі нотатки поза git: NOTES.local.md (питання й відповіді) і DECISIONS.local.md (рішення й відкладені задачі).

12 Типові проблеми й рішення

Проблема Причина й рішення
«Port 8080 was already in use», веб відкрився на 5174 Працює попередній запуск (наприклад, залишений конвеєром для перевірки). lsof -ti :8080 -ti :5173 | xargs kill, потім make up.
«Обліковий запис не прив’язано» Пошта в Keycloak не збігається з поштою в картці члена, або член в архіві, або в Keycloak немає tenant_id.
Не входить admin в адмін-консоль Keycloak Входьте в realm master за адресою /admin/, а не в nadel; перевірте розкладку клавіатури.
У журналі змін «E2E …» та дивні ділянки Сліди старих наскрізних тестів. Скиньте локальну базу (розділ 2); тепер тести працюють на окремій базі.
Попередження «platform (linux/amd64) does not match» для postgres Образ PostGIS лише для Intel, на Mac працює через емуляцію — повільніше, зокрема тести. Заплановано перевірити arm64-образ локально.
Повільні тести бекенду, CI довго Тести бекенду — найдовша частина; заплановано заміряти й прискорити.
Git: «File exists … .lock» Залишився файл блокування після перерваної команди. Переконайтеся, що git не працює, і видаліть указаний .lock.
Зміни в realm-файлі не застосувалися Realm імпортується лише в порожній Keycloak — скиньте локальну базу.
IntelliJ постійно просить доступ до даних інших програм Системні параметри → Конфіденційність і безпека → Повний доступ до диска → IntelliJ IDEA, перезапуск.
Конвеєр зупинився /feature-pipeline resume продовжує з місця зупинки за журналом.
